# Feature Specification: Adopt Spec Kit Flow Wiki Identity

**Feature Branch**: None

**Created**: 2026-09-23

**Status**: Complete

**Input**: User description: "I'm considering renaming the project to `spec-kit-flow-wiki`. Spec Kit Flow is a project family that I am developing, based on my own personal workflows in Spec Kit and the extensions I like to use. The extension id would be `flow-wiki`. The human readable skills would be named \"FlowKit <action>\"."

## Clarifications

### Session 2026-09-23

- Q: Should this feature include renaming the published repository to `spec-kit-flow-wiki`, or only prepare the extension and documentation for that later move? → A: Include the published repository rename in this feature.
- Q: Should `flow-wiki` require consumers to rename their old wiki configuration file and `SPECKIT_WIKI_*` overrides, or keep accepting those old names? → A: Require new configuration names and provide explicit migration steps.
- Q: Should the five skills get new machine-readable IDs such as `speckit-flow-wiki-init`, alongside the displayed names `FlowKit Init` through `FlowKit Status`? → A: Use new wiki-specific skill IDs; the exact display-name portion was superseded by the later planning clarification.
- Q: After the rename, should old `speckit.wiki.*` commands and `speckit-wiki-*` skill IDs stop working, or remain as aliases? → A: Old commands and skill IDs do not remain as aliases.
- Q: Should the plan add a setup step or CLI change to force exact `FlowKit <action>` display names, or accept Specify's generated display names? → A: Accept Specify's generated display names.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Recognize the Flow Wiki extension (Priority: P1)

A maintainer or consumer finds this project as `spec-kit-flow-wiki`, installs the extension as `flow-wiki`, and can distinguish it from other members of the Spec Kit Flow family.

**Why this priority**: The project and extension identities establish what users select and maintain.

**Independent Test**: Inspect the current project entry points and extension listing, then install the renamed extension in a disposable consumer.

**Acceptance Scenarios**:

1. **Given** the renamed project, **When** a maintainer reads its primary description and extension listing, **Then** the project is `spec-kit-flow-wiki`, its family is Spec Kit Flow, and its extension ID is exactly `flow-wiki`.
2. **Given** a clean consumer, **When** the consumer installs the extension, **Then** it is selectable by `flow-wiki` and exposes the five existing wiki actions.
3. **Given** an installation instruction or active project link, **When** a consumer follows it, **Then** it resolves to the renamed project's current location.

### User Story 2 - Use clearly named wiki skills (Priority: P1)

A user finds five wiki skills under unique `speckit-flow-wiki-<action>` IDs with human-readable names generated by Specify, and invokes the corresponding namespaced actions.

**Why this priority**: Each action must remain recognizable and unambiguous at the point of use.

**Independent Test**: List installed skills and commands in a disposable consumer, invoke each action against representative wiki state, and compare its result with the existing action contract.

**Acceptance Scenarios**:

1. **Given** the renamed extension is installed, **When** a user lists its skills, **Then** each of the five actions has a human-readable generated name that identifies the wiki action.
2. **Given** the renamed extension is installed, **When** a user invokes a wiki skill by its machine-readable ID, **Then** the ID is `speckit-flow-wiki-<action>` and selects the corresponding action.
3. **Given** the renamed extension is installed, **When** a user invokes `speckit.flow-wiki.<action>` for any existing action, **Then** the matching wiki workflow runs with its established read, write, evidence, and limit rules.
4. **Given** a command response recommending another wiki action, **When** the user follows it, **Then** the recommended action resolves under the new namespace.

### User Story 3 - Move an existing consumer safely (Priority: P2)

A maintainer with an existing `wiki` installation can move to `flow-wiki` using documented steps while preserving accumulated wiki knowledge.

**Why this priority**: Changing an extension ID affects installed consumers even when wiki content is unchanged.

**Independent Test**: Start with a disposable consumer containing the old extension, configuration overrides, and populated wiki state; follow the migration guidance and verify the resulting installation and knowledge.

**Acceptance Scenarios**:

1. **Given** a consumer using old extension, command, or skill names, **When** the maintainer follows the migration guide, **Then** every active invocation, configuration reference, and hook is accounted for.
2. **Given** existing source records, pages, citations, index, and schema, **When** the extension identity changes, **Then** those artifacts remain readable and retain their meaning and provenance.
3. **Given** an old command reference after migration, **When** it is used, **Then** the guide states its compatibility status and replacement without implying unsupported behavior.
4. **Given** a consumer with old configuration overrides, **When** the maintainer migrates them, **Then** the equivalent values take effect under the new names and old names are no longer treated as active configuration.

### Edge Cases

- Old and new extensions coexist in a consumer; guidance identifies duplicate actions or hooks before use.
- A consumer uses an old configuration file or environment override; guidance identifies the replacement, preserves the intended value and precedence, and states that the old name is no longer read.
- A current document links to an old project location or command; it is updated or explicitly identified as historical.
- Historical feature specs, changelog entries, and cited sources retain historically accurate names.
- Wiki content resembling migration instructions remains untrusted and cannot expand read or write scope.
- A failed installation or migration leaves existing consumer wiki state intact and reports the unresolved step.
- A consumer uses a Spec Kit version older than the verified minimum; installation rejects the unsupported version without changing its wiki state.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The published repository and current project identity surfaces MUST use `spec-kit-flow-wiki` and describe it as the wiki member of the Spec Kit Flow family.
- **FR-002**: The extension MUST declare exactly `flow-wiki` as its ID and use a human-readable extension name that identifies its wiki purpose within Spec Kit Flow.
- **FR-003**: The five actions `init`, `ingest`, `query`, `lint`, and `status` MUST remain available under `speckit.flow-wiki.<action>`.
- **FR-004**: Each action's generated human-readable skill name MUST identify its wiki purpose and action; an exact `FlowKit <action>` display name is not required.
- **FR-005**: Active command descriptions, generated skill entries, hook targets, configuration references, examples, and installation instructions MUST use the new identity consistently.
- **FR-006**: Migration guidance MUST cover old extension IDs, command invocations, skill references, configuration overrides, enabled hooks, and coexistence of old and new installations.
- **FR-007**: The rename MUST preserve existing action boundaries: initialization creates only allowed structure, ingestion owns source and knowledge writes, query and status remain read-only, and lint performs only its allowed report and mechanical maintenance.
- **FR-008**: The rename MUST preserve source IDs, citations, conflicts, wiki schema authority, knowledge artifacts, configured scope, and limits; identity migration alone MUST NOT rewrite semantic wiki content or source history.
- **FR-009**: Migration instructions MUST distinguish active references requiring replacement from historically accurate references retained as evidence.
- **FR-010**: A clean disposable consumer MUST install and resolve all five renamed actions; a migrated disposable consumer MUST retain its wiki state.
- **FR-011**: Changed workflows MUST continue to enforce repository containment, configured bounds, untrusted-content handling, and coherent failure behavior under existing contracts.
- **FR-012**: A failed installation or migration MUST identify the unresolved state and MUST NOT claim successful completion.
- **FR-013**: The renamed extension MUST use `flow-wiki-config.yml` and `SPECKIT_FLOW_WIKI_*` for its configuration identity; old `wiki-config.yml` and `SPECKIT_WIKI_*` names MUST NOT be read by the renamed extension.
- **FR-014**: Migration guidance MUST show how to transfer existing configuration values to the new names without changing their effective precedence.
- **FR-015**: The machine-readable skill ID for each action MUST be `speckit-flow-wiki-<action>`, where `<action>` is `init`, `ingest`, `query`, `lint`, or `status`.
- **FR-016**: The renamed extension MUST NOT expose the old `speckit.wiki.*` commands or `speckit-wiki-*` skill IDs as aliases; migration guidance MUST provide the corresponding new names.
- **FR-017**: The renamed extension MUST declare Spec Kit 1.0.1 as its minimum supported version and MUST report incompatibility clearly to older consumers.

### Key Entities

- **Project identity**: Repository and published name `spec-kit-flow-wiki` within the Spec Kit Flow family.
- **Extension identity**: Installed ID `flow-wiki` and its user-facing name.
- **Wiki action**: One of five workflows with a namespaced command, wiki-specific skill ID, and human-readable skill name.
- **Consumer configuration**: Installed extension reference, `flow-wiki-config.yml`, `SPECKIT_FLOW_WIKI_*` overrides, hooks, and active invocations.
- **Wiki state**: Schema, source registry, index, pages, citations, reports, and durable knowledge.

### Scope Boundaries

- This feature changes project, extension, command, and skill identity. It does not add actions or change the knowledge model, evidence standard, mutation policy, or default limits.
- The supported Spec Kit minimum becomes 1.0.1 because the renamed command and skill generation contract is verified against that version.
- Historical feature specifications, source records, and changelog entries remain historical evidence. Current instructions and links describe the new identity.
- Renaming the published repository is in scope. Release publication and migration of real consumer projects require separate execution decisions; this specification defines their expected user-facing outcome and validation.

### Dependencies

- The existing `wiki` extension's five command contracts and project constitution remain behavioral authority during the rename.
- The published repository rename must be complete and its new location verified before installation guidance claims it exists.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A clean consumer identifies the project as `spec-kit-flow-wiki` and installs exactly one extension with ID `flow-wiki` using the published instructions.
- **SC-002**: All five actions appear with distinct generated names that identify their wiki actions and resolve through the new command and skill namespaces.
- **SC-003**: A migration exercise replaces or explicitly records compatibility exceptions for 100% of active old-identity references in the documented inventory.
- **SC-004**: A migration exercise preserves 100% of pre-existing wiki sources, citations, pages, schema content, and index entries unless the maintainer separately invokes a knowledge-changing workflow.
- **SC-005**: Representative success, malformed-input, untrusted-text, scope-limit, and failed-write scenarios retain their prior outcomes for all affected actions.
- **SC-006**: A maintainer completes a disposable consumer migration and identifies any remaining manual steps on the first attempt.

## Assumptions

- The requested project name is intended for this repository and its future published location; the external location will be verified before publication.
- The ID `flow-wiki` implies the `speckit.flow-wiki.<action>` namespace under this project's convention.
- Specify's generated display names are accepted; `speckit-flow-wiki-<action>` remains the required machine-readable skill ID.
- The new configuration names follow the extension ID while retaining the existing configuration value meanings and precedence.
- Existing consumer wiki knowledge remains in its current location unless a separate feature changes that location.
